# 撰写实验报告

本 skill 把 `docs/0618实验报告.md`（R1）→ `0627实验报告.md`（R2）→ `0704实验报告.md`（R3）→
`0706实验报告.md`（R4）四轮报告中逐步稳定下来的结构和写作规范固化下来，供后续每一轮新实验复用。
**R3/R4 的结构最成熟**，新报告应以它们为主要模板，R1/R2 仅作为早期参照。

## 使用前提

开始写之前，确认手上已经有：

1. 本轮的实验计划文档（`实验计划<日期>.md`），里面有实验分组、变量矩阵、判定标准。
2. 本轮全部实验的原始结果（`results/` 下的 JSON，或已跑过 `aggregate.py` 得到的汇总表）。
3. 上一轮报告，用于承接背景和判断哪些结论是"新的"、哪些是"延续的"。

如果结果还没跑完，先如实告知用户当前完成度，不要用部分数据编出完整结论。

## 报告总体结构

```
# 第 N 轮实验报告（R<N>）

> 承接、日期、硬件、实验规模、种子、训练参数（一段引用块，见下）

## 一、实验总览
  1.1 实验背景（上一轮的核心发现 → 本轮要解决的问题）
  1.2 实验规模（各实验组的数量表）
  1.3 数据集（表格：名称/变量数/维度级别/采样频率/特点）
  1.4 训练参数（epochs/batch_size/lr/patience/seed）
  1.5 方法命名说明（每个方法的简称/全称/技术说明，见下）
  1.6 （如有）机制/参数说明：本轮新引入的开关或融合方式怎么工作
  1.7 模型实现与原始参考仓库的一致性说明（哪些是 bug 修复/有意简化/本研究扩展）

## 二 ~ N-1、各实验组结果（每组一章）
  X.1 实验目的
  X.2 代码改动说明（如果这组涉及模型改动）
  X.3 结果（表格 + 图表）
  X.4 关键发现（现象 + 原因分析，不是简单复述数字）
  X.5 （如有异常现象）专项问题分析

## N、综合分析与结论
  N.1 方法选择矩阵（最终版，如果实验目标是"分场景选方法"）
  N.2 低成本改进结论 / 核心发现总结（5-8 条，编号列表）
  N.3 综合可视化
  N.4 后续建议

## N+1、图表索引（表格：图号/文件名/说明）
```

R3/R4 在"一"和最后"综合分析"两章之外，中间按**实验组**（P0/P1/P2 或 A/B/C/D/E 组）逐章展开，
每章内部严格是"目的 → 结果 → 发现"三段式。**新报告延续这个分组逐章模式**，不要把所有结果堆到一张大表里。

## 分段写作要点

### 引用块（报告开头）

```markdown
> **承接**：第 N-1 轮实验报告（R<N-1>，<日期>）
> **日期**：<起始日期> ~ <结束日期>
> **硬件**：<GPU 型号与数量>
> **实验规模**：<总条数> 次训练（<分组数> 个实验组 × 多条件 × <种子数> 种子）
> **种子**：<种子列表>
> **训练设置**：epochs=<N>, batch_size=<N>, lr=<N>, patience=<N>
```

这几行必须和实际跑的命令、`results/` 里的 JSON 配置一致，不要凭空写。

### 1.1 实验背景

固定写法：先列上一轮报告的 3-5 条核心发现（直接引用它的结论，不要转述走样），再说明"基于以上发现，本轮设定了以下目标"，逐条列出本轮实验组要回答的问题。**每个实验组都要能追溯到背景里的某个问题**，读者不应该看到一个突然冒出来、不知道为什么要做的实验组。

### 1.3 数据集表

固定列：数据集 / 变量数 / 维度级别（低维/中维/高维/超高维） / 采样频率 / 特点（一句话说明这个数据集的性质，比如"多气象变量，变量间相关性强"）。维度级别的划分标准要在报告间保持一致：
- 低维 ≤ 10（ETTh1、ExchangeRate）
- 中维 ~20（Weather）
- 高维 ~300（Electricity）
- 超高维 ~800（Traffic）

### 1.5 方法命名说明

**这是最容易写错的部分。** 每一轮实验里同一个模型可能有多个变体（去模块简化版、原仓库对齐版、消融变体……），命名必须精确到变体级别，绝不能只写"CoIFNet"了事。固定表格：

| 简称 | 全称 | 技术说明 |
|---|---|---|
| Interp+iTransformer | 线性插值填补 + iTransformer 预测器 | 两阶段方法：先线性插值填补缺失，再用 iTransformer（把变量当作 token，学习变量间依赖）预测 |
| MissTSM(grouped_q4) | MissTSM 分组 query 变体，G=4 | 端到端方法：把通道分成 4 组，每组独立可学习 query 做跨变量交叉注意力，输出拼接后投影回原维度 |

技术说明栏要写清楚"这个方法/变体具体怎么运作"，不要只写"效果较好的变体"这种空话。命名一旦在某一轮报告中定下来，后续轮次必须原样沿用，不能改叫法（可以在 1.7 或附录里做"命名对照表"链接旧称呼）。

### 1.7 模型实现与参考仓库一致性说明

如果本轮改动涉及模型代码，必须说明改动的性质，分三类，缺一不可：

1. **bug 修复**：参考实现在语义上有错误（比如 `key_padding_mask` 的 True/False 语义搞反），本实现修正。要点出具体文件、具体行为、修正前后的行为差异。
2. **有意简化**：为了工程简洁性放弃的部分（比如未实现双重 ELBO），要说明放弃了什么、可能有什么影响。
3. **本研究新增的实验扩展**：参考代码里不存在、是本项目为了做消融/验证新增的开关或变体（比如 `grouped_q`、`mask_mode=add`）。

每个模型一段，格式："差异：① xxx（性质标注）；② xxx（性质标注）……"。最后一定要有一句"小结"，概括哪些差异不影响核心设计思想的忠实复现。这一节的价值在于：当后续结果出现"和论文不一致"时，读者能直接判断是不是这里的某条差异造成的，而不用去翻代码。

## 每个实验组章节的写法

### X.1 实验目的

一段话，说明这组实验具体要验证/回答什么问题，引用背景里提出的问题编号（如"验证 Q6：MissTSM 高维优势是否能通过分组 query 进一步增强"）。避免写成"本组实验测试了 XX 方法"这种纯描述，要点出**为什么测**。

### X.2 代码改动说明（如果有改动）

如果这组实验涉及新的模型变体或参数改动，用表格列出改动项、改动前、改动后、参数量变化。参数量变化尤其重要——很多"性能变化"实际上是"参数量变化"造成的，报告里要主动排除或标注这个混淆因素。

### X.3 结果表格

**格式约定**（沿用 R3/R4）：
- 一张表对应一个"数据集 × 缺失类型"组合，行是方法，列是缺失率。
- 数值格式统一写 `MSE / MAE`，并在表格标题下面写清楚"跨种子平均"。
- 改善率/退化率类的表格，正负号约定要在表格上方写明（如"负值=改善，正值=退化"），显著变化（通常 ≥3%）用加粗标出，让读者一眼扫到重点，不需要逐格去读。
- 不要省略"没有变化"的格子——哪怕某组合效果平平，也要如实放进表里，不能只挑好看的结果展示。

### X.4 关键发现——这是报告最核心也最容易写空的部分

每条发现必须是"现象 + 原因分析"的结构，不能只停留在复述数字。参考 R4 报告的写法：

> **不合格写法**："iTransformer(add) 在 ExchangeRate 上有改善，在 Electricity 上有退化。"（只是把表格念了一遍）
>
> **合格写法**："iTransformer(add) 仅在 ExchangeRate 上效果显著：随机点缺失改善幅度从 −2.5%（10%缺失率）递增至 −41.0%（70%缺失率）……ExchangeRate 仅 8 个变量，每个 token 获得掩码信息后可以显著调整注意力权重。在 ETTh1、Weather、Electricity 上，iTransformer(add) 几乎没有改善甚至有退化……"

发现里要主动指出：这个现象和上一轮/上上轮的结论是**吻合还是矛盾**？如果矛盾，要不要在这里给出解释，还是留到后面专项分析。不要回避矛盾的结果，那正是报告最有价值的部分。

**每章 3-5 条发现为宜**，太少显得单薄，太多说明没有提炼。数字优先用表格里已有的数值，不要重新编一套百分比。

### X.5 专项问题分析（异常现象需要时才有）

当出现一个特别反常、值得单独深挖的结果（比如某方法在某条件下 MSE 暴涨 55%），单独开一小节，固定结构：

```
**原因分析**：<从模型结构/数据特性角度解释为什么会发生>
**对比**：<为什么另一个类似方法没有这个问题，衬托出根因确实是刚才分析的那个>
```

不满足"反常到值得深挖"标准的普通波动，放进 X.4 关键发现里一起说即可，不要为了显得严谨而每个数字都单独开一节分析，那样会让真正重要的异常被淹没。

## 可视化

沿用 `scripts/r3_visualize.py`、`scripts/r4_visualize.py` 的模式新建 `scripts/r<N>_visualize.py`：

1. 从 `results/r<N>_*.json`（必要时加上上一轮相关的 `results/r<N-1>_*.json` 做跨轮对比）读取数据，按 `tag` 解析出方法/数据集/缺失率/缺失类型/种子等字段。
2. 用 matplotlib，统一在脚本顶部设置字号（`font.size`、`axes.titlesize` 等）保持风格一致。
3. 输出到项目根目录下的 `figures_r<N>/` 目录（与 `figures_r2/`、`figures_r3/`、`figures_r4/` 同级）。
4. 图表类型按内容选择，不要每组都套同一种图：
   - 方法对比 → 分组柱状图
   - 改善率随维度/缺失率变化 → 热力图（dataset × missing_rate）
   - 多方法多条件全景 → 综合热力图 / 雷达图
   - 缺失率连续趋势 → 折线图

**必须可视化的场景**：跨方法比较（≥3 个方法）、改善率/退化率随缺失率或数据集变化、条件矩阵型结果（判断"什么条件下用什么方法"）。**可以只用表格的场景**：单一数字型结果（参数量对比、单组消融的 2-3 个数值）。

报告正文中每张图前后要有一句说明"图 X：xxx"，图表本身要能独立传达信息（有清晰的坐标轴标签和图例），不要让读者需要反复对照正文才能看懂图。

写完后运行脚本验证图片数量和路径：

```bash
python scripts/r<N>_visualize.py
ls figures_r<N>/*.png | wc -l
```

确认报告中图片引用路径（`../figures_r<N>/xxx.png`，因为报告在 `docs/` 下）都存在。

## 综合分析与结论章节

- **方法选择矩阵**：如果本轮实验的目标是回答"什么条件用什么方法"，用一张表格（行=数据维度，列=缺失类型）给出最终推荐方法，并在备注列写清楚支撑这个推荐的证据来自哪个实验组。
- **核心发现总结**：5-8 条编号列表，每条一段话，是全篇最重要发现的浓缩，一般包括：跨数据集/方法的普遍规律、和上一轮结论的修正或强化、成本收益比最高的改进方案、仍未解决的短板。
- **后续建议**：具体、可执行，指向下一轮实验计划该做什么，不要写"可以进一步研究"这种空话，要写清楚"验证什么、怎么验证"。

## 语言与写作风格

1. **清晰易懂但严谨专业**：长句拆短句；先给结论再给证据（"发现 A——原因是 B"，不要"因为 B，所以观察到 A"这种倒装读起来费力）；专业表述准确，但不堆砌形容词。
2. **减少不必要的英文缩写和外来语混用**：
   - 必须保留的：已经是本项目/领域标准术语的英文（`MSE`/`MAE`、`epoch`/`batch_size`/`seed`/`lr`/`patience`、`GPU`、模型名 `iTransformer`/`PatchTST`/`DLinear`、代码里的参数名如 `hidden`/`d_model`/`mask_mode`）——这些翻译成中文反而增加理解成本，保留原文。
   - 应该替换成中文的：随手夹带的英文连接词或缩写，比如 "vs."→"对比"/"相较于"，"w.r.t."→"关于"，"i.e."/"e.g."→"即"/"例如"，"SOTA"→"当前最优"，"w/"→"带有"。这类词没有技术含义，只是英文写作习惯的残留，中文报告里应该用对应中文表达。
   - 判断标准：如果这个英文词在 `实验计划.md`、代码变量名、或论文原文里就是这个写法，保留；如果只是作者顺手写的英文口语化缩写，换成中文。
3. **表格优先于连续大段文字**：任何涉及"多个方法 × 多个条件"的比较，先给表格，正文解释表格里的发现，不要把数字全部写进段落。
4. **数字要能追溯**：报告里出现的每个百分比/数值，必须能对应到某张结果表或某次 `results/` JSON 聚合，不要在"关键发现"里编出表格中没有的数字。
5. **承认不确定性和局限**：如果某个结论只在 2 个种子下验证、或某个数据集因为显存溢出没跑全，要在报告里明确写出来（参考 R3 报告 1.5 节"CRIB Electricity 显存溢出"的写法），不要把不完整的结果包装成确定结论。
